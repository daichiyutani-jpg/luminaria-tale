# 通信対戦・交換 設計書（未実装）

状態：**設計のみ。サーバーは構築・公開していません。** ゲーム内の「つうしん」画面は「じゅんびちゅう」の案内だけで、通信は一切行いません。

## 1. 方針

- ひとり用は今後も完全オフライン。通信は「つうしん」画面を開いて、自分で部屋を作る／参加した時だけ行う
- 相手とは QR コードでつながる。**QR には部屋に入るための最小限の情報だけ**を入れ、灯獣のデータは入れない
- 勝敗・交換の成立は**サーバーが決める**（端末の申告をそのまま信じない）。改造したデータや同じ灯獣の複製を防ぐ

## 2. QR コードの中身

```
luminaria://room?r=<部屋ID>&t=<参加トークン>&e=<有効期限(UNIX秒)>&v=<通信の版>
```

- 部屋ID：ランダム 10 文字程度
- 参加トークン：その部屋に1回だけ使える使い捨て。サーバー側で署名し、期限は 5 分
- 通信の版：ゲームの通信形式の版。違う版同士は「ゲームを更新してください」と案内して接続しない
- 個人情報・灯獣のデータ・セーブは入れない

## 3. サーバーの役割

| 機能 | 内容 |
| --- | --- |
| 部屋の管理 | 部屋を作る／QR のトークンで参加／2人そろったら開始／期限切れ・放置で自動的に閉じる |
| 持ちこみ検査 | 対戦・交換に出す灯獣を受け取り、`checkMonsterStrict`（`src/save/validate.ts`）と同じ規則で検査する。存在しない技、覚えられない技、レベルと経験値の不一致、素質の範囲外、進化の記録の不整合、ボスの持ちこみ を拒否 |
| 対戦の進行 | 戦闘計算（`src/logic/battle.ts` と同じもの）をサーバーで実行し、乱数もサーバーが持つ。端末は「どの技を使うか」だけを送る。結果はサーバーが両者に配る |
| 交換の成立 | 2段階の確認（下記）。成立した瞬間に、どちらの灯獣がどちらに移ったかをサーバーに記録 |
| 二重取得の防止 | 灯獣ごとの UID と「交換済み記録」を照合し、同じ灯獣を2回出す・交換後に元の端末へ戻す、を拒否 |
| 切断への対処 | 対戦中に切れたら 60 秒まで再接続を待つ。戻らなければ相手の勝ち（記録には残さない練習扱いも選べるようにする）。交換は「確定前に切れたら何も起きない」 |

### 交換の流れ（2段階確認）

1. 両者が出す灯獣を選ぶ → サーバーが検査し、相手の画面に見せる
2. 両者が「この内容で交換する」を押す（どちらかが選び直したら両者の確認は取り消し）
3. サーバーが**1回の処理で**両方の所有を入れ替えて記録し、両者に「受け取り証」（署名つき）を返す
4. 端末は受け取り証を確認してからセーブに反映。送った灯獣はセーブから消す
5. 同じ受け取り証を2回使っても1回分しか反映しない（**冪等キー**＝交換ID）

### 端末側で必要になる変更（実装時）

- セーブに「交換で受け取った／送った灯獣の記録」と「受け取り証」を追加（セーブの版を 2 に上げ、`MIGRATIONS` に移行処理を足す）
- 「つうしん」画面：QR の表示（自前の描画）と読み取り（カメラ。端末の許可が必要）
- 通信中の画面（相手待ち・切断・再接続）

## 4. 置き場所の候補と費用・必要な手続き

| 候補 | 向いている点 | 必要なもの |
| --- | --- | --- |
| Cloudflare Workers ＋ Durable Objects | 部屋ごとに状態を持てる（対戦・交換と相性がよい）。WebSocket 対応。小規模なら無料枠〜月数ドル | Cloudflare のアカウント、支払い方法の登録（Durable Objects は有料プランが必要な場合あり） |
| Firebase（Firestore ＋ Cloud Functions） | 情報が多く作りやすい | Google アカウント、Blaze プラン（従量課金）の登録 |
| Supabase（Postgres ＋ Edge Functions ＋ Realtime） | データベースで記録を管理しやすい | Supabase のアカウント。無料枠あり |

どれを使う場合も、**アカウント作成・支払い方法の登録・公開の操作は本人の作業**になります（このリポジトリの作業では行っていません）。
